# API设计指南

## 1. 概述

本指南定义了分行客户管理系统API的设计原则、规范和最佳实践，旨在确保API的一致性、易用性、安全性和可维护性。所有API开发人员必须严格遵循本指南。

## 2. 设计原则

### 2.1 RESTful API设计原则

- **资源导向**：API设计围绕资源展开，使用名词而非动词表示资源
- **统一接口**：使用标准的HTTP方法（GET、POST、PUT、DELETE等）
- **无状态**：API请求应包含足够的信息，服务器不应存储客户端状态
- **分层系统**：API设计应支持分层架构，允许中间层（如负载均衡器、缓存）介入
- **缓存支持**：API应支持适当的缓存机制，提高性能
- **按需代码**：根据需要提供可执行代码（如JavaScript）

### 2.2 其他设计原则

- **简单易用**：API设计应简单直观，便于客户端开发人员理解和使用
- **一致性**：遵循统一的命名规范、参数格式和响应格式
- **安全性**：确保API的安全性，包括认证、授权、数据加密等
- **可扩展性**：API设计应考虑未来的功能扩展，避免过度设计
- **性能优先**：API应具有良好的性能，响应时间短，资源占用少
- **向后兼容**：API版本升级时应保持向后兼容，避免破坏现有客户端

## 3. 命名规范

### 3.1 资源命名

- 使用**名词复数形式**表示资源集合（如`/visits`、`/gifts`）
- 使用**名词单数形式**表示单个资源（如`/visits/1`、`/gifts/1`）
- 使用**小写字母**和**连字符（-）**分隔单词（如`/gift-applications`）
- 避免使用缩写，除非是广泛认可的缩写（如`API`、`ID`）

### 3.2 参数命名

- 使用**驼峰命名法**（camelCase）命名参数（如`customerName`、`visitDate`）
- 参数名应具有描述性，清晰表达其含义
- 避免使用过于简短的参数名（如`q`、`s`），除非是广泛认可的（如`id`）

### 3.3 HTTP头命名

- 使用**首字母大写的连字符分隔命名法**（Pascal-Case）命名自定义HTTP头（如`X-Request-ID`）
- 遵循HTTP标准头的命名规范

## 4. HTTP方法使用规范

| HTTP方法 | 用途 | 幂等性 | 安全性 |
|----------|------|--------|--------|
| GET | 获取资源 | 是 | 是 |
| POST | 创建资源 | 否 | 否 |
| PUT | 更新资源 | 是 | 否 |
| DELETE | 删除资源 | 是 | 否 |
| PATCH | 部分更新资源 | 否 | 否 |
| HEAD | 获取资源头信息 | 是 | 是 |
| OPTIONS | 获取资源支持的HTTP方法 | 是 | 是 |

### 4.1 具体使用场景

- **GET**：用于获取资源，不修改资源状态
- **POST**：用于创建新资源或执行非幂等操作
- **PUT**：用于更新整个资源（替换）
- **PATCH**：用于部分更新资源（推荐使用JSON Patch格式）
- **DELETE**：用于删除资源

## 5. 状态码使用规范

### 5.1 成功状态码

| 状态码 | 描述 | 使用场景 |
|--------|------|----------|
| 200 OK | 请求成功 | 通用成功响应，用于GET、PUT、DELETE等 |
| 201 Created | 资源创建成功 | 用于POST请求创建资源成功 |
| 204 No Content | 无内容 | 用于DELETE请求成功，或PUT/PATCH请求成功但无需返回内容 |
| 304 Not Modified | 资源未修改 | 用于缓存验证，客户端可以使用缓存的资源 |

### 5.2 客户端错误状态码

| 状态码 | 描述 | 使用场景 |
|--------|------|----------|
| 400 Bad Request | 请求参数错误 | 用于请求格式错误、缺少必填参数、参数值无效等 |
| 401 Unauthorized | 未授权 | 用于缺少认证信息或认证失败 |
| 403 Forbidden | 禁止访问 | 用于认证成功但无权限访问资源 |
| 404 Not Found | 资源不存在 | 用于请求的资源不存在 |
| 405 Method Not Allowed | 不允许的HTTP方法 | 用于使用了不支持的HTTP方法 |
| 406 Not Acceptable | 不可接受的响应格式 | 用于客户端请求的响应格式不被支持 |
| 415 Unsupported Media Type | 不支持的媒体类型 | 用于请求的媒体类型不被支持 |
| 429 Too Many Requests | 请求过多 | 用于客户端请求频率超过限制 |

### 5.3 服务器错误状态码

| 状态码 | 描述 | 使用场景 |
|--------|------|----------|
| 500 Internal Server Error | 服务器内部错误 | 用于服务器端发生未预期的错误 |
| 501 Not Implemented | 未实现 | 用于请求的功能尚未实现 |
| 502 Bad Gateway | 网关错误 | 用于作为网关或代理服务器时，从上游服务器收到无效响应 |
| 503 Service Unavailable | 服务不可用 | 用于服务器暂时无法处理请求（如维护、过载） |
| 504 Gateway Timeout | 网关超时 | 用于作为网关或代理服务器时，未及时从上游服务器收到响应 |

## 6. 响应格式规范

### 6.1 成功响应格式

- **单个资源响应**：直接返回资源对象
  ```json
  {
    "id": 1,
    "customerName": "张三",
    "visitDate": "2023-01-01T10:00:00",
    "visitContent": "拜访客户，讨论合作事宜"
  }
  ```

- **资源列表响应**：返回包含分页信息的对象
  ```json
  {
    "total": 100,
    "page": 1,
    "size": 10,
    "data": [
      {
        "id": 1,
        "customerName": "张三",
        "visitDate": "2023-01-01T10:00:00",
        "visitContent": "拜访客户，讨论合作事宜"
      },
      // 更多资源...
    ]
  }
  ```

### 6.2 错误响应格式

所有错误响应应遵循统一格式：

```json
{
  "code": "ERROR_CODE",
  "message": "错误描述信息",
  "details": "可选的详细错误信息"
}
```

- **code**：错误代码，用于客户端程序判断错误类型
- **message**：错误描述，简明扼要地描述错误原因
- **details**：详细错误信息，可选，用于开发调试

### 6.3 示例错误响应

```json
{
  "code": "INVALID_REQUEST",
  "message": "请求参数错误",
  "details": "缺少必填参数：customerName"
}
```

## 7. 参数规范

### 7.1 查询参数

- **分页参数**：使用`page`（页码，从1开始）和`size`（每页大小）表示分页
- **过滤参数**：使用资源字段名作为过滤条件（如`customerName=张三`）
- **排序参数**：使用`sort`参数表示排序，格式为`字段名:方向`，多个排序条件用逗号分隔（如`sort=visitDate:desc,customerName:asc`）
- **日期参数**：使用ISO 8601格式表示日期和时间（如`2023-01-01`、`2023-01-01T10:00:00`）

### 7.2 请求体参数

- 使用**JSON格式**作为请求体（Content-Type: application/json）
- 字段名使用**驼峰命名法**（camelCase）
- 必填字段应在API文档中明确标记
- 提供合理的默认值，减少必填字段数量

## 8. 安全性规范

### 8.1 认证与授权

- **认证方式**：使用基于Session的认证，通过Cookie传递会话令牌（JSESSIONID）
- **授权方式**：使用RBAC（基于角色的访问控制）模型
- **权限检查**：所有API端点必须进行适当的权限检查
- **敏感数据**：敏感数据（如密码）在传输和存储过程中必须加密

### 8.2 数据安全

- **输入验证**：对所有客户端输入进行严格验证，防止SQL注入、XSS等攻击
- **输出编码**：对API响应数据进行适当编码，防止客户端XSS攻击
- **数据过滤**：根据用户权限过滤响应数据，确保用户只能访问其有权限的数据

### 8.3 传输安全

- **HTTPS**：所有API请求和响应必须使用HTTPS加密传输
- **HTTP头安全**：设置适当的HTTP安全头（如Content-Security-Policy、X-Content-Type-Options等）

## 9. 版本控制

### 9.1 版本号格式

使用**主版本号.次版本号.修订号**格式（如1.0.0），其中：
- **主版本号**：当API发生不兼容的重大变更时递增
- **次版本号**：当API增加功能但保持向后兼容时递增
- **修订号**：当API修复错误但不影响功能时递增

### 9.2 版本控制方式

- **URL路径版本控制**：将版本号包含在URL路径中（如`/api/v1/visits`）
- **请求头版本控制**：通过自定义请求头（如`Accept-Version: 1.0.0`）指定版本

本系统采用**URL路径版本控制**方式。

### 9.3 版本支持策略

- 同时支持至少两个主版本
- 旧版本在新版本发布后至少支持6个月
- 提前3个月通知客户端关于旧版本的废弃计划

## 10. 性能优化

### 10.1 响应时间要求

- **核心API**：响应时间不超过500ms
- **非核心API**：响应时间不超过1000ms
- **复杂查询API**：响应时间不超过3000ms

### 10.2 优化措施

- **缓存机制**：对频繁访问的数据使用缓存（如Redis）
- **分页查询**：所有列表查询必须支持分页，默认每页10条记录
- **按需加载**：支持选择性返回资源字段，减少数据传输量
- **异步处理**：对耗时操作采用异步处理，返回任务ID供客户端查询状态
- **数据库优化**：合理设计数据库索引，优化查询语句

## 11. 文档规范

### 11.1 API文档要求

- **完整性**：所有API端点必须有完整的文档
- **准确性**：文档必须与实际API实现保持一致
- **可读性**：文档应清晰易懂，包含示例请求和响应
- **更新及时性**：API变更后必须及时更新文档

### 11.2 文档格式

使用**OpenAPI 3.0**规范编写API文档，文档文件名为`openapi.yaml`，位于`api-contracts`目录下。

## 12. 测试要求

### 12.1 测试类型

- **单元测试**：对API的各个组件进行单元测试，覆盖率不低于80%
- **集成测试**：测试API组件之间的交互
- **端到端测试**：测试完整的API流程
- **性能测试**：测试API在高并发场景下的性能
- **安全性测试**：测试API的安全性，包括渗透测试、漏洞扫描等

### 12.2 测试工具

- **单元测试**：使用JUnit、Mockito等
- **API测试**：使用Postman、Swagger UI等
- **性能测试**：使用JMeter、LoadRunner等
- **安全性测试**：使用OWASP ZAP、Burp Suite等

## 13. 监控与日志

### 13.1 监控要求

- **API调用监控**：监控API的调用次数、响应时间、错误率等指标
- **系统资源监控**：监控服务器的CPU、内存、磁盘、网络等资源使用情况
- **告警机制**：当API指标超过阈值时，触发告警通知

### 13.2 日志要求

- **日志级别**：使用DEBUG、INFO、WARN、ERROR、FATAL五个级别
- **日志内容**：包含时间戳、请求ID、用户ID、API端点、HTTP方法、响应状态码、响应时间等信息
- **日志格式**：使用JSON格式，便于日志分析工具处理
- **日志存储**：日志应集中存储，便于查询和分析

## 14. 最佳实践

### 14.1 API设计最佳实践

- **设计优先**：在实现API之前，先设计API文档，确保API的合理性和易用性
- **用户体验优先**：从客户端开发人员的角度出发，设计简单易用的API
- **避免过度设计**：API设计应简洁明了，避免不必要的复杂性
- **考虑错误处理**：提供清晰的错误信息，帮助客户端开发人员调试
- **使用HTTP标准**：遵循HTTP标准和RESTful API设计原则

### 14.2 开发最佳实践

- **代码复用**：避免重复代码，提取公共组件和工具类
- **模块化设计**：API实现应采用模块化设计，便于维护和扩展
- **代码质量**：遵循良好的编码规范，保持代码的可读性和可维护性
- **自动化测试**：编写自动化测试用例，确保API的质量和稳定性
- **持续集成**：使用CI/CD工具，实现API的自动构建、测试和部署

## 15. 变更管理

### 15.1 API变更流程

1. **需求分析**：分析API变更需求，评估变更影响
2. **设计变更**：更新API设计文档
3. **实现变更**：修改API实现代码
4. **测试验证**：进行充分的测试验证
5. **文档更新**：更新API文档
6. **发布通知**：向客户端开发人员发布API变更通知
7. **灰度发布**：逐步推广新API，监控其表现
8. **正式发布**：全面切换到新API
9. **旧版废弃**：按照版本支持策略废弃旧版API

### 15.2 变更影响评估

在API变更前，必须评估变更对现有客户端的影响，包括：
- **向后兼容性**：变更是否破坏现有客户端
- **性能影响**：变更是否影响API性能
- **安全影响**：变更是否引入安全风险
- **依赖影响**：变更是否影响其他API或系统

## 16. 附则
