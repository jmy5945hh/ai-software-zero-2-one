## 文档说明

本文档记录"招财银行北京分行运营门户系统"的关键架构决策，采用 ADR（Architecture Decision Records）格式，包括决策内容、理由、影响和替代方案。

**ADR 格式**:
- **编号**: ADR-001, ADR-002, ...
- **日期**: 决策日期
- **状态**: 提案中 / 已采纳 / 已废弃 / 已替代
- **决策**: 决策标题
- **背景**: 为什么需要这个决策
- **决策内容**: 具体的决策内容
- **理由**: 选择该方案的理由
- **影响**: 对系统的影响
- **替代方案**: 考虑过但未采纳的方案

## 1. 技术选型决策

### ADR-001: 采用前后端分离架构

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统需要支持多角色用户，包含数据可视化、AI 助理等复杂功能，需要良好的用户体验和可维护性。

**决策内容**:
采用前后端分离架构，前端使用 React + TypeScript，后端使用 FastAPI + Python，通过 RESTful API 通信。

**理由**:
1. **职责分离**: 前端专注于用户体验，后端专注于业务逻辑
2. **并行开发**: 前后端可独立开发和测试，提高开发效率
3. **技术栈匹配**: 团队对前后端技术栈都有经验
4. **可扩展性**: 前后端可独立扩展和部署
5. **AI 友好**: React 和 FastAPI 都是 AI 训练数据丰富的技术栈

**影响**:
- **正面**: 开发效率高，可维护性好，易于测试
- **负面**: 需要管理两套代码，部署复杂度略高
- **技术债**: 需要维护 API 契约一致性

**替代方案**:
1. **单体架构**: 前后端代码在一起（如传统的 Django 模板渲染）
   - 优点: 部署简单
   - 缺点: 前后端耦合，难以并行开发，用户体验差

2. **微服务架构**: 按业务模块拆分多个服务
   - 优点: 独立扩展，技术灵活
   - 缺点: 过度设计，运维复杂度高，不适合当前规模

**相关决策**:
- ADR-002: RESTful API 设计
- ADR-003: JWT 认证机制

### ADR-002: 采用 RESTful API 风格

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
前后端需要通过 HTTP 接口通信，需要确定接口设计风格。

**决策内容**:
采用 RESTful API 风格，使用 HTTP 动词（GET/POST/PUT/DELETE）和资源路径，数据格式为 JSON。

**理由**:
1. **标准化**: REST 是业界标准，易于理解和维护
2. **工具支持**: FastAPI 自动生成 OpenAPI/Swagger 文档
3. **缓存友好**: GET 请求可被浏览器和代理缓存
4. **测试简单**: 可用 curl/Postman 直接测试
5. **前端集成**: Axios 和 React Hooks 天然支持 RESTful

**影响**:
- **正面**: 接口清晰，文档自动生成，易于调试
- **负面**: 需要严格遵循 REST 规范，可能增加接口数量
- **技术债**: 需要管理 API 版本

**替代方案**:
1. **GraphQL**: 前端灵活查询数据
   - 优点: 前端灵活，减少请求次数
   - 缺点: 后端复杂度高，学习曲线陡峭，过度设计

2. **gRPC**: 基于 HTTP/2 的高性能 RPC
   - 优点: 性能高，类型安全
   - 缺点: 不适合浏览器直接调用，需要 API 网关

**设计原则**:
- 使用名词表示资源（如 `/api/v1/visits`）
- 使用 HTTP 动词表示操作（GET 查询，POST 创建，PUT 更新，DELETE 删除）
- 使用 HTTP 状态码表示结果（200 成功，400 客户端错误，500 服务器错误）
- 使用查询参数过滤和排序（如 `/api/v1/visits?status=success&sort=-create_time`）

**相关决策**:
- ADR-001: 前后端分离架构
- ADR-005: API 版本策略

### ADR-003: 采用 JWT 认证机制

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统需要支持多角色权限控制，前后端分离架构下需要安全的认证机制。

**决策内容**:
采用 JWT（JSON Web Token）认证机制，用户登录后颁发 Access Token，前端每次请求在 Header 中携带 Token，后端验证 Token 有效性。

**理由**:
1. **无状态**: Token 自包含用户信息，服务端不需要存储会话
2. **跨域友好**: 适合前后端分离和跨域部署
3. **性能优秀**: 无需查询数据库验证会话
4. **标准化**: JWT 是业界标准，库支持完善
5. **扩展性好**: 可在 Token 中携带角色和权限信息

**影响**:
- **正面**: 无状态认证，易于水平扩展，性能好
- **负面**: Token 无法主动撤销，需要依赖过期时间
- **技术债**: 需要妥善管理 JWT Secret Key

**Token 配置**:
- 算法: HMAC SHA256 (HS256) 或 SM2/SM3（国密，待确认）
- 过期时间: 120 分钟（2 小时）
- 存储位置: 前端 localStorage（需注意 XSS 防护）
- 传输方式: HTTP Header `Authorization: Bearer <token>`

**替代方案**:
1. **Session + Cookie**: 传统会话机制
   - 优点: 可主动撤销，安全性高
   - 缺点: 有状态，难以水平扩展，不适合前后端分离

2. **OAuth 2.0**: 第三方授权标准
   - 优点: 标准化，支持第三方登录
   - 缺点: 复杂度高，过度设计，不需要第三方登录

**相关决策**:
- ADR-001: 前后端分离架构
- ADR-008: 安全架构设计

### ADR-004: 采用 SQLAlchemy ORM

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
后端需要与 MySQL 数据库交互，需要选择数据访问层技术。

**决策内容**:
采用 SQLAlchemy 2.x ORM 框架，使用声明式模型定义数据库表结构。

**理由**:
1. **成熟稳定**: Python 生态最成熟的 ORM
2. **AI 友好**: 声明式模型清晰，AI 易于生成和维护
3. **数据库无关**: 支持多种数据库，迁移方便
4. **性能优秀**: 连接池、懒加载、批量操作等性能优化
5. **类型安全**: 配合 Pydantic 和 Mypy 可实现类型检查

**影响**:
- **正面**: 开发效率高，代码可读性好，易于维护
- **负面**: ORM 有一定学习成本，复杂查询性能可能不如原生 SQL
- **技术债**: 需要管理数据库迁移脚本

**替代方案**:
1. **原生 SQL**: 直接编写 SQL 语句
   - 优点: 性能最优，灵活
   - 缺点: 开发效率低，易注入，难以维护

2. **Tortoise ORM**: 异步 ORM，类似 Django ORM
   - 优点: 异步性能好
   - 缺点: 生态不如 SQLAlchemy，AI 生成支持不好

3. **SQLModel**: Pydantic + SQLAlchemy 的结合
   - 优点: 类型定义简洁
   - 缺点: 生态不成熟，功能有限

**相关决策**:
- ADR-007: 数据库选型
- ADR-011: 数据库表设计

### ADR-005: 采用 Zustand 状态管理

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
前端需要管理全局状态（用户信息、权限、AI 对话历史等），需要选择状态管理方案。

**决策内容**:
采用 Zustand 作为全局状态管理库，管理用户信息、权限、AI 对话历史等全局状态。

**理由**:
1. **轻量简洁**: 代码量少（约 1KB），无模板代码
2. **易于理解**: API 简单，学习成本低
3. **AI 友好**: 代码结构清晰，AI 易于生成和维护
4. **性能优秀**: 细粒度订阅，避免不必要的渲染
5. **TypeScript 友好**: 类型推导完善

**影响**:
- **正面**: 代码简洁，易于维护，性能好
- **负面**: 需要团队学习新库（但学习成本低）
- **技术债**: 无

**替代方案**:
1. **Redux**: 传统的状态管理方案
   - 优点: 生态成熟，中间件丰富
   - 缺点: 模板代码多，复杂度高，过度设计

2. **React Context**: React 内置状态管理
   - 优点: 无需第三方库
   - 缺点: 性能差（全量渲染），不适合复杂场景

3. **Jotai / Recoil**: 原子化状态管理
   - 优点: 细粒度更新
   - 缺点: 概念抽象，学习成本高

**相关决策**:
- ADR-001: 前后端分离架构

### ADR-006: 采用 Pydantic v2 数据校验

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
后端需要校验请求数据和序列化响应数据，需要选择数据校验方案。

采用 Pydantic v2 作为数据校验和序列化框架，定义 Request/Response Model。

- **负面**: 需要定义数据模型，增加少量代码

1. **手动校验**: 使用 if 语句手动校验
   - 优点: 灵活

2. **Marshmallow**: 独立的数据校验库

## 2. 架构模式决策

### ADR-007: 采用分层架构模式

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
后端需要组织代码结构，确定模块划分和依赖关系。

**决策内容**:
采用经典的三层架构模式：API 路由层（Routers）→ 业务逻辑层（Services）→ 数据访问层（Repository/ORM）。

**理由**:
1. **关注点分离**: 每层职责单一，易于理解和维护
2. **可测试性**: 业务逻辑与框架解耦，易于单元测试
3. **可扩展性**: 各层可独立扩展和替换
4. **团队协作**: 前端对接 API 层，后端实现 Service 层
5. **AI 友好**: 分层清晰，AI 易于生成代码

**层次职责**:

| 层级 | 职责 | 示例 |
| --- | --- | --- |
| **API 路由层** | 定义路由、参数解析、调用 Service | `@router.post("/visits")` |
| **业务逻辑层** | 实现业务规则、事务管理、权限控制 | `VisitService.create_visit()` |
| **数据访问层** | 数据库 CRUD、查询构建 | `session.query(CustomerVisit).filter_by(...)` |

**影响**:
- **正面**: 代码结构清晰，易于维护和测试
- **负面**: 增加代码层级，可能过度设计
- **技术债**: 需要团队遵守分层规范

**替代方案**:
1. **MVC 模式**: Model-View-Controller
   - 优点: 经典模式
   - 缺点: View 层在前端，不适合前后端分离

2. **洋葱架构**: 领域驱动设计
   - 优点: 业务逻辑独立，可测试性高
   - 缺点: 过度设计，当前业务场景不需要

**相关决策**:
- ADR-001: 前后端分离架构
- ADR-004: SQLAlchemy ORM

## 3. 数据存储决策

### ADR-008: 采用 MySQL 8.0+ 数据库

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统需要持久化存储业务数据，需要选择数据库技术。

**决策内容**:
采用 MySQL 8.0+ 作为关系型数据库，存储用户、拜访记录、礼品申请等业务数据。

**理由**:
1. **企业级标准**: 银行等金融行业首选数据库
2. **功能丰富**: JSON 支持、CTE（公共表表达式）、窗口函数
3. **性能优秀**: InnoDB 引擎，事务支持完善
4. **生态成熟**: 监控、备份、高可用方案成熟
5. **团队经验**: 团队对 MySQL 熟悉，学习成本低

**影响**:
- **正面**: 稳定可靠，功能完善，易于维护
- **负面**: 关系型数据库扩展性有限（但当前规模不需要）
- **技术债**: 需要管理数据库连接池和迁移脚本

**替代方案**:
1. **PostgreSQL**: 开源关系型数据库
   - 优点: 功能更丰富（如 JSON 查询、全文搜索）
   - 缺点: 团队不熟悉，银行场景 MySQL 更常见

2. **MongoDB**: NoSQL 文档数据库
   - 优点: 灵活，扩展性好
   - 缺点: 不支持事务，不适合金融场景

**相关决策**:
- ADR-004: SQLAlchemy ORM

### ADR-009: 不使用 Redis 缓存（当前阶段）

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统是否需要引入 Redis 缓存来提升性能。

**决策内容**:
当前阶段不引入 Redis 缓存，所有数据直接从 MySQL 读取。后续如性能瓶颈再考虑引入。

**理由**:
1. **避免过度设计**: 并发用户量 < 100，MySQL 性能足够
2. **简化架构**: 减少组件，降低运维复杂度
3. **数据一致性**: 避免缓存与数据库不一致问题
4. **成本控制**: 减少 Redis 服务器资源

**影响**:
- **正面**: 架构简单，易于维护，数据一致性好
- **负面**: 无法缓存热点数据，性能可能略低
- **技术债**: 如需引入缓存，需改造代码

**何时引入 Redis**:
- 单接口响应时间 > 2 秒
- 数据库 CPU 使用率 > 80%
- 需要缓存会话数据（如 JWT 黑名单）
- 需要分布式锁

**替代方案**:
1. **引入 Redis 缓存**: 缓存热点数据
   - 优点: 性能提升
   - 缺点: 增加复杂度，缓存一致性问题

**相关决策**:
- ADR-003: JWT 认证机制
- ADR-008: MySQL 数据库

   - 缺点: API Key 暴露，不安全

2. **部署本地模型**: 部署开源大模型（如 Llama）

## 5. 安全策略决策

### ADR-011: 采用 RBAC 权限模型

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统需要支持 4 种角色（客户经理、运营人员、审批人员、分行管理者），需要确定权限控制模型。

**决策内容**:
采用 RBAC（Role-Based Access Control）权限模型，基于角色控制用户访问权限。

**理由**:
1. **简单有效**: 符合业务场景，易于理解
2. **标准化**: 业界标准，实现方案成熟
3. **易于维护**: 角色和权限分离，便于调整
4. **性能优秀**: JWT Token 中携带角色信息，无需查询数据库

**角色定义**:

| 角色 | 代码 | 权限范围 |
| --- | --- | --- |
| 客户经理 | CUSTOMER_MANAGER | 登记拜访记录、提交礼品申请、查看个人数据 |
| 运营人员 | OPERATIONS | 维护首页内容、查看运营数据、查看礼品台账 |
| 审批人员 | APPROVER | 审批礼品申请、查看审批历史 |
| 分行管理者 | MANAGER | 查看运营数据大屏、查看所有统计数据 |

**影响**:
- **正面**: 权限控制清晰，易于实现和维护
- **负面**: 不支持细粒度权限（如字段级权限）
- **技术债**: 如需细粒度权限，需升级为 ABAC

**替代方案**:
1. **ABAC**: 基于属性的权限控制
   - 优点: 灵活，支持细粒度权限
   - 缺点: 复杂度高，过度设计

2. **ACL**: 访问控制列表
   - 优点: 灵活
   - 缺点: 难以维护，不推荐

**相关决策**:
- ADR-003: JWT 认证机制
- ADR-008: 安全架构设计

### ADR-012: 前端采用路由守卫 + 后端采用依赖注入鉴权

**日期**: 2026-01-08
**状态**: 已采纳

**背景**:
系统需要实现权限控制，防止未授权访问。

**决策内容**:
前端使用 React Router 路由守卫控制页面访问，后端使用 FastAPI 依赖注入验证每个请求的权限。

**理由**:
1. **纵深防御**: 前后端双重验证，提高安全性
2. **用户体验**: 前端拦截，避免无权限请求
3. **安全性**: 后端强制验证，防止绕过前端
4. **代码清晰**: 依赖注入复用性高，易于维护

**前端实现**:
```typescript
// 路由守卫示例
const ProtectedRoute = ({ roles, children }) => {
  const { user } = useAuthStore();
  if (!user) return <Navigate to="/login" />;
  if (roles && !roles.includes(user.role)) return <Navigate to="/403" />;
  return children;
};
```

**后端实现**:
```python
# 依赖注入示例
def get_current_user(token: str = Depends(oauth2_scheme)) -> User:
    return verify_token(token)

def require_role(roles: List[str]):
    def decorator(func):
        @wraps(func)
        async def wrapper(user: User = Depends(get_current_user)):
            if user.role not in roles:
                raise HTTPException(403, "无权限访问")
            return await func(user)
        return wrapper
    return decorator
```

**影响**:
- **正面**: 安全性高，代码复用性好
- **负面**: 增加代码量
- **技术债**: 无

**替代方案**:
1. **仅后端鉴权**: 前端不做权限控制
   - 优点: 前端代码简单
   - 缺点: 用户体验差，无权限请求多

**相关决策**:
- ADR-003: JWT 认证机制
- ADR-011: RBAC 权限模型
