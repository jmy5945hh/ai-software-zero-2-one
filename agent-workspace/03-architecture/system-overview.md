### 1.2 前后端分离架构说明

系统采用经典的前后端分离架构：

1. **职责分离**:
   - 前端负责页面渲染、用户交互、状态管理
   - 后端负责业务逻辑、数据持久化、权限控制

2. **通信方式**:
   - 前后端通过 RESTful API 进行通信
   - 数据格式: JSON
   - 认证方式: JWT (JSON Web Token)

3. **部署独立性**:
   - 前端打包为静态资源，可部署在 Nginx/CDN
   - 后端为独立服务，可独立扩展和部署

## 2. 技术栈选型

### 2.1 技术栈总览

| 层级 | 技术选型 | 版本 | 选型理由 |
| --- | --- | --- | --- |
| **前端框架** | React | 18+ | 生态成熟，AI 友好，组件丰富 |
| **前端语言** | TypeScript | 5.0+ | 类型系统，提高代码质量和可维护性 |
| **构建工具** | Vite | 5.0+ | 极速启动，HMR 快速，开发体验好 |
| **UI 组件库** | Ant Design | 5.x | 中文 B 端标准，组件丰富，文档完善 |
| **状态管理** | Zustand | latest | 轻量简洁，无模板代码，易于理解 |
| **数据可视化** | ECharts | 5.x | 图表丰富，中文文档，国内标准 |
| **HTTP 请求** | Axios + useRequest | latest | 经典请求库 + React Hooks 工具 |
| **路由** | React Router | v6 | 单页应用标准，API 友好 |
| **后端框架** | FastAPI | 0.110+ | 现代 Python Web 框架，类型支持好 |
| **后端语言** | Python | 3.10+ | 类型系统成熟，AI 生成稳定 |
| **Web Server** | Uvicorn | latest | ASGI 服务器，性能优秀 |
| **数据校验** | Pydantic | v2 | 强类型数据契约，与 FastAPI 深度集成 |
| **ORM** | SQLAlchemy | 2.x | 成熟 ORM，声明式模型，AI 友好 |
| **数据库** | MySQL | 8.0+ | 企业级标准，JSON/CTE 支持 |
| **字符集** | utf8mb4 | 默认 | 中文 + 表情 + 扩展字符支持 |

### 2.2 前端技术栈选型理由

#### React 18+
- **生态成熟**: 社区庞大，第三方库丰富，问题容易解决
- **AI 友好**: 训练数据多，AI 生成代码准确率高
- **性能优秀**: 虚拟 DOM + 并发渲染，用户体验好
- **就业市场**: 国内前端招聘主流技术栈

#### TypeScript 5.0+
- **类型安全**: 编译期捕获错误，减少运行时 Bug
- **代码可读性**: 类型即文档，降低维护成本
- **AI 辅助**: AI 理解业务逻辑的关键，生成代码更准确
- **重构友好**: 类型检查让重构更安全

#### Vite 5.0+
- **极速启动**: 基于 ES Modules，冷启动秒级
- **HMR 快速**: 模块热更新，开发体验好
- **配置简单**: 零配置即可使用，开箱即用
- **生态完善**: 插件丰富，社区活跃

#### Ant Design 5.x
- **中文 B 端标准**: 国内企业级应用首选 UI 库
- **组件丰富**: 覆盖 90% 以上业务场景
- **文档完善**: 中文文档详尽，示例丰富
- **设计规范**: 企业级设计语言，用户体验一致
- **ProComponents**: 高阶业务组件，减少代码量

#### Zustand
- **轻量简洁**: 代码量少，无模板代码
- **易于理解**: API 简单，学习成本低
- **AI 友好**: 代码结构清晰，AI 易于生成和维护
- **性能优秀**: 细粒度订阅，避免不必要渲染

### 2.3 后端技术栈选型理由

#### FastAPI 0.110+
- **现代 Python 框架**: 基于 Python 3.6+ 类型提示
- **自动文档**: 自动生成 OpenAPI/Swagger 文档
- **类型安全**: Pydantic 数据校验，减少运行时错误
- **高性能**: 基于 Starlette，性能接近 NodeJS 和 Go
- **AI 友好**: 类型提示和依赖注入让 AI 生成代码更准确
- **异步支持**: 原生支持 async/await，并发性能好

#### Python 3.10+
- **类型系统成熟**: typing 模块完善，Pydantic v2 支持
- **AI 生成稳定**: Python 是 AI 训练数据最多的语言之一
- **生态丰富**: 第三方库丰富，开发效率高
- **易读易维护**: 语法简洁，团队协作友好

#### SQLAlchemy 2.x
- **成熟 ORM**: Python 生态最成熟的 ORM
- **声明式模型**: 数据模型清晰，AI 易于生成
- **数据库无关**: 支持多种数据库，迁移方便
- **性能优秀**: 连接池、懒加载等性能优化

#### MySQL 8.0+
- **企业级标准**: 银行等金融行业首选数据库
- **功能丰富**: JSON 支持、CTE、窗口函数
- **性能优秀**: InnoDB 引擎，事务支持完善
- **生态成熟**: 监控、备份、高可用方案成熟

## 3. 系统边界定义

### 3.1 系统内部边界

系统内部按功能模块划分边界：

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| **认证模块** | 用户登录、JWT 颁发、权限验证 | 用户表 |
| **拜访管理模块** | 拜访记录 CRUD、查询统计 | 拜访记录表、用户表 |
| **礼品管理模块** | 礼品申请、审批、台账 | 礼品申请表、礼品表、用户表 |
| **内容管理模块** | 轮播图、新闻 CRUD | 轮播图表、新闻表、用户表 |
| **数据大屏模块** | 运营指标统计、图表数据 | 拜访记录表、礼品申请表 |
| **AI 助理模块** | 对话接口、上下文管理 | 外部 LLM API |

### 3.2 系统外部边界

#### 包含的外部依赖
- **MySQL 数据库**: 本地部署，数据持久化
- **火山引擎 LLM API**: AI 问答功能

#### 不包含的外部系统
- 核心银行系统
- CRM 系统
- HR 系统
- OA 系统

### 3.3 数据边界

| 数据类型 | 存储位置 | 所有权 |
| --- | --- | --- |
| 用户数据 | MySQL users 表 | 系统管理员维护 |
| 业务数据 | MySQL 各业务表 | 业务用户创建和修改 |
| 配置数据 | 环境变量 / MySQL | 系统管理员维护 |
| 会话数据 | JWT Token (客户端) | 客户端存储 |
| AI 对话历史 | 可选: MySQL 或 Redis | 待确认 |

## 5. 架构原则

### 5.1 设计原则

1. **关注点分离**: 前后端分离，模块职责单一
2. **高内聚低耦合**: 模块内部高内聚，模块间低耦合
3. **可测试性**: 业务逻辑与框架解耦，易于单元测试
4. **可扩展性**: 预留扩展点，支持功能迭代
5. **安全性**: 纵深防御，多层安全控制

### 5.2 技术约束

1. **前后端分离**: 必须采用 RESTful API 通信
2. **类型安全**: 前后端必须使用强类型（TypeScript + Python typing）
3. **文档先行**: 所有 API 必须有 OpenAPI/Swagger 文档
4. **环境隔离**: 开发、测试、生产环境配置分离

## 6. 架构风险与缓解措施

| 风险 | 影响 | 概率 | 缓解措施 |
| --- | --- | --- | --- |
| AI API 不稳定 | AI 助理不可用 | 中 | 添加超时和重试机制，提供友好错误提示 |
| 数据库性能瓶颈 | 系统响应慢 | 低 | 合理索引、查询优化、读写分离（可选） |
| 前后端接口契约不一致 | 联调困难 | 中 | 使用 OpenAPI 文档，契约测试 |
| 安全漏洞 | 数据泄露 | 低 | 代码审查、安全扫描、渗透测试 |
