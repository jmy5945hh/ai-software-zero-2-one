# v0.2 Spec: 软件研发端到端交付

## 背景

v0.1 已经证明了 AI 研发流程可以被拆成需求、设计、编码、质量、验证、交付等节点，但 showcase 暴露出三个核心短板：

- 交付结果缺少系统级测试证据，用户难以相信代码可用。
- 节点确认过多，用户需要理解流程细节，提效感被削弱。
- 入口仍偏任务看板，尚未覆盖“一句话做应用”和工程任务的一站式体验。

v0.2 的目标不是增加更多节点，而是把平台定位从“AI 按 SOP 写代码”升级为“AI 交付经过验证的软件任务”。

## 目标

1. 统一入口：用户从一个自然语言输入开始，平台自动识别任务类型并分流。
2. 低认知负担：用户只选择自治等级、运行位置和少量策略，不逐节点审批。
3. 测试后交付：每个任务都形成可追溯的验证计划、验证结果和交付报告。
4. 成本可控：SOP 节点声明能力需求，运行态按策略路由模型。
5. 可继续演进：Agent 能力、测试能力、模型策略和交付证据都以结构化配置沉淀。

## 用户入口

首页使用一个统一交付工作台，不再把“自由输入”和“团队任务”拆成两个入口：

- 上方约 1/3 是 AI 任务输入区。顶部切换 `Plan / Builder / Workflow`，输入框下方就近选择模型策略、Skills、MCP 和仓库分支。
- 下方约 2/3 是任务模板面板，通过 Tab 切换“故事卡开发 / Bugfix / 治理任务 / 检视问题”。
- 点击任务卡只注入任务上下文和该类型的推荐参数，不立即执行；用户可以回到同一输入框补充或修改后再启动。
- 自由输入和任务模板最终调用同一个任务初始化与执行链路，不形成两套产品模式。

入口遵循渐进披露：模型、Skills、MCP、仓库是贴近输入的高频上下文；自治等级、验证范围、自动修复和风险确认收进交付设置。仓库可以提前配置，执行时直接复用；未配置时才在首次启动补齐。

`deliveryConfig` 作为统一入口的持久化契约，除交付模式、自治等级和验证策略外，还记录：

- interactionMode：Plan / Builder / Workflow
- modelId：Auto 或运行时已经配置的具体模型
- modelPolicy：自动路由 / 质量优先 / 成本优先
- skills：本次任务挂载的技能
- mcpServers：本次任务连接的 MCP

更细的 SOP 节点和测试项配置仍由模板与运行态策略决定，不阻塞主流程。

## 黑盒测试范围

v0.2 的系统级验证不只包含 Web 页面和 API，还应覆盖：

- Web E2E：页面打开、核心路径、表单、弹窗、状态变化。
- API 合约：状态码、字段结构、错误返回、鉴权、幂等性。
- 业务场景：按用户故事串联页面、接口、数据和状态。
- 数据持久化：刷新、重启、切换页面后状态保留。
- 异常恢复：空数据、超时、接口失败、重复点击、断网。
- 权限安全：未授权访问、越权、危险命令、敏感信息泄露。
- 响应式兼容：桌面、窄屏、关键浏览器视口。
- 性能冒烟：首屏、接口延迟、大文件或长任务下的可用性。
- 可观测性：失败时是否有日志、截图、trace 和可定位错误。

## Agent 能力矩阵

| Agent | 职责 | 主要输入 | 主要输出 |
| --- | --- | --- | --- |
| Intent Router Agent | 识别任务类型、风险和是否需要 UI 原型 | 用户输入、项目状态 | deliveryConfig、workflow routing |
| Test Planner Agent | 生成验证计划和验收矩阵 | 需求、设计、代码 diff | test-plan.json |
| Web QA Agent | 执行页面级黑盒测试 | URL、用户路径、断言 | 截图、trace、E2E 结果 |
| API QA Agent | 执行接口契约和异常测试 | API 路由、调用样例、鉴权 | API 测试报告 |
| Business Scenario Agent | 串联业务用户故事 | 验收标准、页面/API 映射 | 场景通过/失败证据 |
| Failure Triage Agent | 归因失败原因 | 测试输出、日志、diff | 修复建议、风险等级 |
| Repair Loop Agent | 将失败反馈给开发 Agent | 失败证据、代码上下文 | 修复 patch、复测请求 |
| Delivery Report Agent | 生成最终交付报告 | diff、测试结果、风险 | delivery-report.md |

## 流程

```text
统一入口
  -> 意图分流与风险识别
  -> 生成验收标准和测试计划
  -> 开发实现
  -> 自动运行黑盒测试和质量门禁
  -> 失败归因与自动修复
  -> 复测
  -> 交付报告
```

在产品操作上，质量阶段提供“一键验证并生成报告”主操作，自动串联：

1. 生成 `verification_plan.json`
2. 执行安全可自动化验证并写入 `verification_result.json`
3. 汇总 `DELIVERY.md`

Web/API/业务场景若当前无法自动执行，不应伪造通过结果，而应在 `verification_result.json` 中标记为 blocked/skipped，并等待专用 QA Agent 或人工证据回填。

当前 v0.2 已内置一层保守 API QA 探测器：

- 只允许探测 `localhost`、`127.0.0.1`、`::1` 上的只读 GET 接口。
- 默认对本平台 Agent runtime 探测 `/health` 和 `/api/resources`。
- 探测结果写入 `verification_result.json`，包含状态码、期望状态码、是否通过和响应预览。
- 不允许向外部域名发送请求，也不自动提交表单或执行有副作用的接口。

用户确认不再绑定每个节点，而是绑定风险：

- 需求歧义需要业务判断。
- 删除文件、数据库、鉴权、部署、生产配置等高风险操作。
- 引入新依赖、大范围重构、成本或时间超阈值。
- 验证失败但 Agent 建议继续交付。

## SOP 与模型策略

每个 SOP 节点应声明：

- agentId
- capability
- defaultModelTier
- reasoningMode
- allowedTools
- contextInputs
- outputArtifacts
- verificationGate
- retryPolicy
- escalationPolicy
- budgetHint

模型不应硬编码在节点中。运行态由 `SOP Step Config + Runtime Policy + Model Router` 决定实际模型：

- 小模型：意图分类、摘要、上下文压缩、简单检查。
- 中模型：常规代码修改、测试生成、文档整理。
- 大模型：架构权衡、复杂 debug、跨模块重构、最终审查。
- 工具优先：lint、typecheck、unit test、Playwright、API runner。

升级条件包括失败重试、风险升高、跨模块影响扩大、上下文不确定性过高。

## v0.2 交付验收

- 首页默认呈现统一自然语言入口，而不是把用户先推入任务泳道。
- 自由输入与四类任务 Tab 位于同一工作台，任务卡点击后回填输入区并允许微调。
- 任务启动前能选择交互模式、模型策略、Skills、MCP、仓库分支和高级交付设置。
- 已选择仓库可直接复用，未选择仓库时才在首次启动补齐。
- 任务初始化元数据包含 deliveryConfig，后续 Agent runtime 可消费。
- Workflow 中质量与验证的文案体现黑盒测试、业务场景和交付证据。
- 质量阶段提供一键验证交付操作，能生成验证计划、执行结果和交付报告三类证据产物。
- 文档沉淀 v0.2 的入口、测试、Agent、SOP 和模型策略。
