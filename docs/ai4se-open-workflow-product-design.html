Product Owner View

把研发流程变成用户可拥有的 AI 团队

开放 workflow 的价值不是让用户配置更多字段，而是让 CTO、技术负责人、产品负责人把自己的研发方法复制给平台， 并在真实任务中不断校准。用户要获得的不是一个流程编辑器，而是一个可以被训练、被解释、被治理、被复用的交付系统。

一句话创建体验 草案待确认
“我想要一个偏前端体验验证的研发流程：需求后先做竞品和用户路径分析，再生成交互原型，确认后编码，最后跑 E2E 和发布检查。”
Workflow 草案 6 个节点，2 个用户确认关口，1 个可跳过分支。
Agent 节点 新增 UX Analyst，复用 Prototype / Coding / QA。
运行预览 展示输入、产物、权限、失败恢复和预计耗时。
01 / Product Thesis

用户真正购买的是“可复制的研发判断力”

固定 AI4SE workflow 证明了平台能跑通一个标准研发任务；开放体系要证明平台能承载不同团队的研发方法。 产品应把复杂配置折叠成用户熟悉的语言：团队方法、角色分工、交付关口、可验证产物。

用户痛点

AI 会做事，但不懂我的团队方法

不同组织有自己的评审节奏、合规要求、设计偏好和交付标准。固定流程只能演示能力，无法沉淀组织经验。

产品机会

让方法从“口头经验”变成“可运行资产”

用户不需要从零设计 Agent。他只要描述方法，平台生成可读、可改、可试跑的团队流程。

差异化

不是自动化编排，而是研发组织建模

节点不是脚本步骤，而是带有职责、技能、工具、产物、权限和用户协作方式的 AI 成员。

02 / Users

先服务“会定义研发方式”的人

早期不要面向所有用户做全量自由配置。优先服务能清楚表达研发方法、同时又希望降低执行成本的人。 他们不是为了玩配置，而是为了让团队稳定复用一套更好的交付方式。

03 / Core Journey

从“使用模板”到“拥有自己的 AI 研发组织”

用户旅程要像搭建团队，而不是像配置流水线。每一步都给用户一个明确的收益，并让复杂度只在需要时展开。

1
选择起点

从 AI4SE 默认模板、团队模板、历史任务或一句话开始。

2
描述方法

用自然语言说明想要新增的角色、关口、产物或质量标准。

3
AI 生成草案

平台输出 workflow、Agent、Skills/MCP 建议和运行预览。

4
试跑校准

在一个真实任务中观察每个节点是否有价值，快速调整。

5
发布复用

保存为团队方法，后续任务可直接选择并持续积累版本。

04 / Experience Principles

降低认知负担的 6 条产品原则

开放能力会天然变复杂。产品必须把自由度包在清晰的默认路径里，让用户先获得结果，再逐步理解和控制细节。

先问目标，不先问配置

入口文案应该是“你想让 AI 团队如何工作？”，不是“请选择节点类型”。

草案先行，配置后置

一句话生成的结果先进入草案态。用户看懂后确认，才发布成正式模板。

每个节点都必须解释自己的价值

节点卡片默认显示职责、输入、输出、用户何时介入、为什么需要这个节点。

画布不是第一界面

先用“流程预览 + Agent 详情抽屉”承载主要体验；画布只服务复杂流程编辑。

把工具名翻译成能力语言

用户选择“读取 Figma”“查数据库”“跑浏览器测试”，而不是先理解 MCP server 名称。

运行时比设计时更重要

用户最终信任的不是模板编辑页，而是真实任务中每步产物、决策、权限和回退都清楚。

05 / Product Shape

核心界面：AI 团队工作台

06 / Key Interaction

一句话创建不是魔法按钮，而是协同设计流程

AI 生成 workflow/agent 的体验应该包含“生成、解释、模拟、确认”四步。用户不需要相信黑盒，平台要把 AI 的设计理由显性化。

“我想让平台像一个懂我们团队习惯的研发负责人，而不是每次都像新来的实习生。”
1. 生成

从一句话提取交付目标、关键角色、必要关口、质量标准和约束。

2. 解释

每个节点说明“为什么需要、如果删除会损失什么、什么任务会跳过”。

3. 模拟

用一个示例任务预演：节点顺序、用户介入点、预计产物、风险提示。

4. 发布

先试跑，再发布。发布后成为团队模板，进入版本管理。

07 / Agent Node Model

创建 Agent 节点时，用户看见的是“职责卡”

Agent 节点不应以 Prompt 编辑器开场。用户先定义职责、产物、判断边界，再由平台生成可编辑 Prompt。 高级用户仍可进入 Sys Prompt、Skills、MCP、模型和权限。

Role

它是谁

角色名称、专业领域、适用任务类型、与其他 Agent 的边界。

Mission

它负责什么

一句话使命、成功标准、必须避免的行为、需要用户确认的事项。

Materials

它读写什么

输入材料、上下文来源、输出产物、交接给下游节点的格式。

Powers

它能调用什么

Skills、MCP、文件权限、命令权限、外部系统权限和审批要求。

08 / Skills & MCP

把工具市场设计成“能力货架”

大多数用户不关心 MCP 协议细节。他们关心某个 Agent 是否能访问设计稿、查需求系统、跑浏览器、读数据库、发 PR。 因此配置入口应按能力组织，再映射到底层 Skills / MCP。

Discover

按任务发现能力

当用户创建“UX Analyst”，系统推荐设计观察、截图分析、竞品网页读取，而不是给一串工具列表。

Trust

每项能力有风险等级

只读、写文件、执行命令、访问外部系统、产生费用等风险要清晰标识，默认最小授权。

Audit

运行后可追踪

任务记录中展示每个 Agent 用过哪些能力、读取了什么、写了什么、哪些操作经过用户确认。

11 / Architecture Mapping

技术只是把产品语言翻译成可执行资产

架构上保留当前固定 workflow 的成功经验，把“任务级路由契约”升级成通用运行清单。产品语言是团队方法， 技术语言才是 definition、node、resource、session。

Workflow Definition

团队方法模板

节点顺序、条件、用户关口、默认 Agent、适用范围、版本和发布状态。

Agent Definition

AI 成员定义

职责卡、Sys Prompt、Prompt Template、Skills、MCP、权限、输入输出契约。

Run Manifest

任务运行快照

某次任务实际使用的 workflow 版本、节点状态、跳过原因、产物路径、session 映射和回退点。

12 / Risks

开放体系的最大风险不是做不出来，而是让用户不敢用

越开放越需要默认治理。产品必须让用户知道：AI 为什么这么做、能做什么、不能做什么、做坏了怎么恢复。

!
配置过载
用“一句话创建 + 草案解释 + 渐进高级配置”降低进入门槛。
!
Agent 权限失控
每个能力绑定风险等级，默认只读，写入/命令/外部动作可审批。
!
Workflow 跑完但价值不明
每个节点必须有产物、评价标准和下游消费方；无产物节点默认不建议保留。
!
模板越改越乱
草案、试跑、发布、版本回退分层；运行时冻结配置，避免历史任务漂移。

一句话结论

AI4SE 开放体系的产品目标不是“让用户自定义流程”，而是“让用户把自己的研发组织能力产品化”。 最好的第一版，是从当前标准 workflow 出发，让用户用自然语言调整团队方法、生成可解释草案、在真实任务中试跑，并把有效方法沉淀为可复用模板。
