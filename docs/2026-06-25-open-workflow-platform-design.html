AI Team Builder

让用户像组建真实团队一样，组建自己的AI软件交付团队。
从「平台定义流程」到「用户定义流程」。

01 — 问题

一个流程，无法适配所有团队

现在的AI4SE平台是一条固定管道。所有任务——无论大小、类型、团队——都走同一条路。这就像给所有病人开同一种药。

1

流程僵化

修一个CSS bug要走完6步？做数据迁移脚本需要"交互原型"？固定流程对大量场景是浪费。

2

Agent不可复用

我们有个很好的"产品经理"Agent，但只能用在需求分析这一步。能不能让它参与代码review？

3

配置是黑箱

System Prompt、Tools、Skills——这些决定了Agent能力的核心配置，用户完全看不到、改不了。

4

无法扩展

想加一个"API文档生成"Agent？需要改5个文件、理解整个架构。扩展成本太高。

02 — 愿景

从「执行管道」到「组建团队」

用户不是想要一个"工作流编辑器"。用户想要的是——我有一群AI专家，我来决定他们怎么协作。

06 — Agent 创建

像招聘一样，创建你的AI专家

三种创建方式，从最简单到最灵活。

从模板开始

预置6个专业角色：产品经理、原型设计师、架构师、全栈工程师、测试工程师、DevOps。一键使用，按需微调。

适合：快速搭建，不想从零配置

用自然语言描述："我需要一个专门做API文档的Agent，要能读代码、生成OpenAPI规范、写用户文档。"AI生成完整配置。

适合：有明确需求，想快速得到结果

07 — 设计决策

关键决策与理由

每个决策都服务于核心原则：降低认知负担，保持一致体验。

Agent所有权：工作流私有

每个工作流独立持有自己的Agent定义。改一个工作流的Agent不影响其他。原因：降低"修改一个影响全局"的风险，用户可以放心实验。

运行时：可配置检查点

默认全自动执行，但支持在任意步骤设置暂停点。原因：CTO用户既要效率（全自动）又要控制力（关键节点人工确认）。

编辑器：垂直管道视图

不用复杂的节点+连线画布，而是简洁的垂直列表。原因：线性流程不需要图编辑器，垂直管道更符合"从上到下"的阅读习惯。

MCP：声明式配置

用户配置MCP Server的启动命令和参数，运行时自动连接。原因：最简单有效，不需要内置市场，用户自己管理MCP Server。

存储：JSON文件

工作流和Agent配置存储为JSON文件。原因：原型阶段最简单，易于版本管理，后续可平滑迁移到数据库。

共存：并存模式

现有固定workflow保留为"AI4SE标准团队"预置模板，新系统作为高级模式。原因：零迁移成本，用户渐进式采用。

08 — 技术架构

数据驱动，配置与运行分离

核心改造：把硬编码的STEP_CONFIGS变成可存储、可编辑的WorkflowConfig数据。

09 — 实施路线

渐进式交付，每阶段可验证

6个阶段，每阶段独立交付价值。P0-P2是基础能力，P3-P5是增值体验。

阶段 范围 核心产出 验证标准
P0 数据层 WorkflowConfig 类型定义、WorkflowStore (JSON CRUD)、REST API 可通过API创建/读取/更新/删除工作流配置
P1 运行时 AgentRunner 动态配置加载、WorkflowEngine 线性调度、检查点暂停 用JSON配置的工作流可以完整运行，暂停/继续正常工作
P2 编辑器 垂直管道视图、Agent配置面板 (Prompt/Tools/模型)、添加/删除/重排步骤 用户可在可视化编辑器中完成工作流的完整配置
P3 AI创建 Copilot 对话界面、自然语言→WorkflowConfig生成、应用到编辑器 用户输入一句话描述，30秒内得到可运行的工作流
P4 模板系统 预置Agent模板库 (6个角色)、从模板创建工作流、模板管理 用户可以从模板一键创建团队，模板覆盖80%常见场景
P5 Skills & MCP Agent级 Skills 挂载、MCP Server 声明式配置、MCP 运行时连接 用户可以为Agent配置Skills和MCP，运行时正常加载
关键原则：P0-P1完成后，现有的"AI4SE标准团队"就可以作为第一个WorkflowConfig JSON运行。这意味着现有功能不会中断，同时为开放体系打下基础。
10 — 待讨论

还需要一起想清楚的事

现有固定workflow的迁移

是把当前硬编码逻辑转为一个"AI4SE标准"的WorkflowConfig JSON（统一数据驱动），还是保留两套代码？我倾向前者。

Agent模板的深度

模板应该包含完整的AgentConfig（含systemPrompt），还是只包含骨架让用户填充？完整模板更易用，骨架更灵活。

运行视图的复用

自定义工作流运行时，是复用现有TaskPage（改造成通用渲染器），还是新建独立执行视图？

多工作流并行

用户能否同时运行多个工作流？当前架构假设单任务单工作流。多工作流需要会话隔离。
