# v0.2 任务执行工作台整体设计

## 1. 设计结论

任务执行页回归行业通行的三栏工作台，不再让 Workflow 独占主视觉：

1. 左侧是任务区：当前任务、任务上下文、轻量流程导航。
2. 中间是自然语言轮次交互区：始终可见，是用户与 Agent 协作的主视图。
3. 右侧是工作台：Web 预览、代码变更、Terminal、阶段产出。

Workflow 不是第四个区域，也不再作为“交付 / 轨迹”互斥 Tab。它是一层贯穿三栏的任务状态：

- 中间任务标题栏告诉用户“现在在哪、正在做什么、是否需要我介入”。
- 左侧当前任务项允许低成本展开完整流程和历史节点。
- 中间只在节点开始、完成、失败、等待确认时插入轻量流程事件。
- 右侧按节点聚合关键产出和验证证据。
- 当前节点完成后，在对话输入框上方提供统一推进操作。

## 2. 当前体验为何失效

当前页面的能力并不弱，主要问题是信息架构违背用户习惯：

- “交付 & 协作”和“任务轨迹”互斥，用户无法同时看对话和产出。
- 横向 SOP 导航、交付策略条、节点头部重复表达流程，抢占首屏。
- Workspace 入口在左侧，阶段产出在中间，预览和 Terminal 继续以弹窗或局部卡片出现，工具心智不统一。
- 点击历史流程节点同时改变 `stepIndex`，把“查看历史”与“改变执行位置”混为一件事。
- 阶段完成后的推进操作分散在不同产出组件中，用户需要先理解当前页面结构。

本次不是换皮，而是把已有能力放回用户熟悉的位置。

## 3. 页面骨架

### 3.1 桌面端

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ 项目 / 任务  │ 任务标题  Workflow · 编码 3/7  │ [预览] [终端] [代码] [产出] │
├──────────────┼────────────────────────────────┼─────────────────────────────┤
│ 任务区       │ 自然语言轮次交互区             │ 真实运行工作台              │
│ 16%-18%      │ 40%-44% / 主视觉               │ 38%-42% / 主视觉            │
│              │                                │                             │
│ 项目 A       │ 任务原始描述                   │ 127.0.0.1:5173              │
│  ├ 任务 1    │                                │ ┌─────────────────────────┐ │
│  └ 当前任务  │ 用户消息                       │ │                         │ │
│     ● 3/7    │ Agent 回复                     │ │  正在运行的真实应用      │ │
│              │ 已编辑 4 个文件 · 运行 2 条命令│ │                         │ │
│ 展开流程     │                                │ └─────────────────────────┘ │
│  ✓ 需求分析  │ ─ 编码开发完成 ─               │                             │
│  ✓ 技术设计  │ 已生成 4 个文件 · 构建通过     │                             │
│  ● 编码开发  │                                │                             │
│  ○ 质量审查  │                                │                             │
│              │ [查看产出] [进入质量审查 →]    │                             │
│              │ ┌────────────────────────────┐ │                             │
│              │ │ 输入消息，继续和 AI 协作… │ │                             │
│              │ └────────────────────────────┘ │                             │
└──────────────┴────────────────────────────────┴─────────────────────────────┘
```

推荐默认比例为 `10% / 50% / 40%`，最小约束为 `220px / 520px / 480px`。两条分隔线可拖动，但设置只保存在本地，不进入任务业务状态。

该比例与行业典型形态一致：左侧只负责项目和任务导航；中间保留连续对话；右侧优先展示正在运行的真实应用，而不是平台信息卡片。

### 3.2 中等宽度

在 1100-1360px：

- 左侧任务区收为 72px 图标栏，点击后临时展开。
- 中间对话保持主视觉。
- 右侧工作台保持至少 420px。
- Workflow 节点只显示状态点和短标签。

### 3.3 窄屏

在小于 900px 时不强行保留三列：

- 默认显示对话。
- 顶部使用 `任务 / 对话 / 工作台` 三个视图 Tab。
- 当前 Workflow 状态收进对话标题栏。
- 用户切到工作台后，内部仍保留 `预览 / 代码 / 终端 / 产出`。

## 4. Workflow 的四层表达

### 4.1 第一层：中间任务标题栏

不新增横跨三栏的 Workflow 导航。在中间对话区标题旁放一个小型状态胶囊：

```text
设计可转债 AI 策略系统    Workflow · 编码开发 3/7 · 运行中
```

状态胶囊只回答三个问题：

- 当前在哪个节点。
- 当前是运行、等待用户、失败还是完成。
- 点击后在哪里查看完整流程。

节点运行时显示细进度动画；等待用户时使用高可见但克制的提示色；失败时显示“验证失败 · 查看”。节点产出和下一步操作不塞进标题栏，分别留在对话事件和推进操作条。

### 4.2 第二层：左侧当前任务展开态

左侧首先保持行业熟悉的“项目 / 任务列表”。当前任务行只显示一个小型 Workflow 状态点和 `3/7`；点击状态或“展开流程”，在当前任务下原位展开节点：

- 已完成：勾选 + 产物数量。
- 当前：实心状态点 + 一行任务摘要。
- 待执行：低对比圆点，不可直接启动。
- 有阻塞：错误标识 + 简短原因。

点击已完成节点进入“历史查看态”，只切换中间对话和右侧产物的查看范围，不改变实际执行进度。

### 4.3 第三层：对话中的流程事件

对话区不展示每个内部工具步骤，只在关键边界插入事件：

- 节点开始。
- 阶段产物生成。
- 等待用户决策。
- 节点完成。
- 验证失败与自动修复。

事件默认只有一行摘要，例如：

```text
✓ 技术设计完成 · 2 个文档 · 3 个关键决策        查看产出
```

工具调用、思考过程、Token 用量继续保留在轮次折叠详情中，避免抢占自然语言对话。

### 4.4 第四层：推进操作条

固定在对话输入框上方，随状态变化：

| 状态 | 主操作 | 次操作 |
| --- | --- | --- |
| Agent 运行中 | 继续对话 / 中止 | 查看实时 Terminal |
| 等待用户 | 提交回答 | 查看上下文 |
| 节点已完成 | 进入下一阶段 | 查看阶段产出 |
| 验证失败 | 自动修复并复测 | 查看失败证据 |
| 高风险操作 | 确认继续 | 调整方案 |
| 全流程完成 | 查看交付报告 | 返回任务列表 |

推进始终在同一位置完成，阶段组件不再各自发明主按钮。

## 5. 三大区域详细设计

### 5.1 左侧任务区

信息顺序：

1. 新建任务、搜索、已安排等通用入口。
2. 按仓库或项目分组的任务列表。
3. 当前任务高亮、运行状态和更新时间。
4. 当前任务可原位展开 Workflow 轻量节点。
5. 任务级操作菜单：重命名、复制任务 ID、回退任务、归档。

左侧不再展示大块“当前任务详情卡”，也不承载 Workspace 工具按钮。任务详情保留在中间对话的首条任务描述中，历史节点摘要通过悬停或点击节点查看。

### 5.2 中间自然语言轮次区

中间区始终展示当前“查看节点”的会话：

- 顶部小标题显示节点名称；若查看历史节点，明确标记“历史产出，只读”。
- 第一条固定为任务原始描述，可折叠。
- 用户消息和 Agent 回复沿用 Chat 心智。
- Tool Call 默认折叠为一行，展开后查看命令、文件和结果。
- 输入框固定在底部，支持继续对话、回答问题、补充需求和中止。

不再设置“交付 & 协作 / 任务轨迹”Tab。自然语言协作是默认视图，阶段产出进入右侧工作台。

### 5.3 右侧工作台

右侧是与中间对话同等级的真实运行画布。顶部沿用浏览器 / IDE 的轻量工具栏，并提供四个稳定 Tab：

| Tab | 内容 | 默认出现阶段 |
| --- | --- | --- |
| 预览 | 默认主视图；Web 预览、原型 iframe、运行 URL、刷新与设备尺寸 | 原型、编码、验证 |
| 代码 | 文件树、Diff、单文件预览、回退入口 | 编码以后 |
| 终端 | 构建、测试、QA 输出、运行进程、受控命令输入 | 编码、质量、验证 |
| 产出 | Spec、技术方案、验收清单、测试证据、交付报告 | 全阶段 |

Tab 顺序稳定，预览始终排第一。系统只更新徽标和推荐态，不强制替用户切 Tab。首次进入节点时，如果用户尚未主动选择过，才应用节点默认 Tab：

- 需求分析 / 技术设计：产出；若已有运行应用，仍记住用户上次的预览选择。
- 交互原型：预览。
- 编码开发：预览；代码 Tab 用徽标提示新增变更。
- 质量审查 / 黑盒验证：终端。
- 发布交付：产出。

### 5.4 阶段产出

产出不再以散落卡片占据主区，统一建模并进入“产出”Tab：

```ts
type WorkflowArtifact = {
  id: string;
  stepId: WorkflowId;
  type: "document" | "preview" | "code" | "test" | "report";
  title: string;
  status: "generating" | "ready" | "failed" | "blocked";
  path?: string;
  updatedAt: string;
  evidenceSummary?: string;
};
```

当前节点产出置顶，历史节点产出按阶段折叠。状态数量同步回左侧节点徽标和中间标题状态胶囊。

## 6. 必须拆开的两个状态

当前 `stepIndex` 同时承担“任务执行到哪里”和“用户正在查看哪里”，需要拆开：

```ts
type WorkflowViewState = {
  executionStepId: WorkflowId;
  viewingStepId: WorkflowId;
  workbenchTab: "preview" | "code" | "terminal" | "artifacts";
  taskPaneCollapsed: boolean;
  workbenchWidth?: number;
};
```

- `executionStepId` 只能由 Workflow 推进动作改变。
- `viewingStepId` 允许用户自由回看已完成节点。
- 当两者不同，中间区显示“历史查看态”，输入框默认仍作用于当前执行节点，并明确提示目标节点。
- 用户点击待执行节点只查看节点说明，不提前创建 Agent Session。

这项拆分是本次 UX 能否成立的前提。

## 7. 关键状态体验

### 7.1 Agent 正在工作

- 中间对话流式输出。
- 中间标题状态胶囊显示当前动作。
- Terminal / 代码 Tab 更新徽标，不自动抢焦点。
- 用户可以继续发消息进行 steer，也可以中止。

### 7.2 等待用户决策

- 输入框上方出现唯一高优先操作条。
- 对话自动定位到问题轮次。
- 左侧当前节点出现等待标记。
- 工作台保持用户当前 Tab，不弹出阻塞式全屏 Modal。

### 7.3 节点完成

- 对话插入完成事件。
- 右侧“产出”Tab 增加 ready 徽标。
- 推进操作条展示“进入下一阶段”。
- 不自动推进，也不强迫用户先打开产出；自治模式允许倒计时后自动推进，但可随时取消。

### 7.4 失败与自动修复

- 失败证据进入 Terminal / 产出 Tab。
- 中间只显示归因摘要，不倾倒原始日志。
- 主操作为“自动修复并复测”，次操作为“查看失败证据”。
- 修复发生在当前节点，不虚假推进 Workflow。

## 8. 从现状到目标的组件映射

| 当前组件 | 目标位置 | 处理方式 |
| --- | --- | --- |
| `SopNav` | 中间标题状态胶囊 + 左侧当前任务展开态 | 拆分显示层，复用同一 `taskWorkflow` |
| `DeliveryStrategyBanner` | 顶部任务配置 Popover | 默认收起，不再占整行 |
| `LeftPanel` | 左侧任务区 | 保留任务上下文，移出 Workspace |
| `TrajectoryChatTab` | 中间对话区 | 取消 Tab 包裹，成为常驻主视图 |
| `DeliveryCollabTab` | 右侧“产出”Tab | 复用产出、决策和验证组件 |
| `WorkspaceExplorer` | 右侧“代码”Tab | 保留 RepoExplorer、Diff、回退能力 |
| `BuildSection` / QA Terminal | 右侧“终端”Tab | 汇总构建、测试和 QA 输出 |
| `PrototypePreview` / `Drawer` | 右侧“预览”Tab | 常驻 iframe，抽屉仅用于全屏查看 |

本次不重写 Agent 协议、Session、Workflow 路由和验证接口，只重组呈现层并补齐视图状态。

## 9. 不做什么

- 不再新增第四个 Workflow 主区。
- 不保留全宽大 Stepper、全宽交付策略条和节点重复标题。
- 不把每个 Tool Call 都渲染成流程节点。
- 不允许查看历史节点改变真实执行进度。
- 不自动切换工作台 Tab 打断用户。
- 不用大量卡片包装页面区域。

## 10. 设计验收标准

1. 用户进入任务页后，首屏同时看到任务、对话和工作台。
2. 用户不展开流程也能知道当前节点、状态和下一步。
3. 用户最多一次点击即可看到完整流程或当前阶段产出。
4. 用户查看历史节点时不会改变任务实际执行位置。
5. 对话始终可见，阶段产出和 Terminal 不再与对话互斥。
6. 推进、回答、修复、放行等主操作始终出现在输入框上方同一位置。
7. Web 预览、代码、Terminal、产出使用稳定 Tab，不随节点改变信息架构。
8. Workflow、对话和产物状态来自同一个 `taskWorkflow + session + artifact` 状态源。

## 11. 建议确认的三个设计决策

1. 桌面端是否接受 `任务区 / 对话区 / 工作台` 三栏固定骨架，默认比例为 `17% / 43% / 40%`。
2. 是否同意取消“交付 & 协作 / 任务轨迹”互斥 Tab，让对话常驻、产出进入右侧工作台。
3. 是否同意拆分 `executionStepId` 和 `viewingStepId`，将历史节点点击定义为只读查看。

确认这三点后，再进入组件级交互稿和开发。
